This job reduces many logs to a one-page summary, so use `list.fold`, with the `Summary` record itself as the accumulator. The empty summary `Summary(0, 0, 0, None)` is the initial value, and `add_entry(summary, entry) -> Summary`, which applies one log, is the folding function.

`add_entry` first increases `total`, which is shared by every log, and then increases the per-level field with `case entry.level`. Because `Level` is a sum type, the compiler checks that you handled all four levels (theory note "Sum types and exhaustive matching"). If you move the shared update outside the `case`, the mistake of forgetting `total` in one branch simply can't happen, by construction. That is exactly the common mistake: if you write `Debug -> summary` to mean "just skip the levels I don't care about", debug logs drop out of the total.

`first_critical` must record "only the first one". `option.or(summary.first_critical, Some(entry.message))` picks the existing value if there is one, and the new message otherwise. If you overwrite with `Some(entry.message)` every time, the last critical log is what remains. A fold visits each element once from the front, so the difference between "first" and "last" comes down to whether you overwrite (theory note "The universality of fold: the common skeleton of list recursion").
