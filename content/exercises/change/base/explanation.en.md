Picking the largest coin first (the greedy method) fails for some sets of denominations. To make 23 from `[1, 4, 15, 20, 50]`, picking 20 first means you need three more 1s, for 4 coins, but 4 + 4 + 15 is just 3. To make 27 from `[4, 5]`, picking five 5s first leaves 2, and you are completely stuck.

The right starting point is **optimal substructure**. If you remove one coin c from the smallest combination for amount a, the remaining coins must be the smallest combination for amount a - c. So the answer for a is the smallest of "1 + (the answer for a - c)" over every coin c (`dynamic-programming-subproblems`).

If you write this formula directly as recursion, the answer is correct, but the answers for small amounts get recomputed over and over, and the number of calls grows exponentially with the amount. At 999 it never finishes. There are only target + 1 subproblems, the amounts 0..target, so if you compute them in order starting from 0, store them in a `Dict` and read them back when needed, the total cost is O(amount x number of coin types).

The solution stores `#(number of coins, coins used)` in the table. Keeping the count separately means you do not have to recount with `list.length` when comparing candidates, and `[coin, ..used]` shares the previous amount's list without copying it (`cost-model-immutable-structures`). Amounts that cannot be made are simply left out of the table, so `Error(Nil)` from `dict.get` naturally means "impossible". Marking them with a special value such as 0 or a huge number mixes them up with real values and invites mistakes (`errors-as-values`). Finally, sort the result in ascending order. The order of the coins built up in the table depends on the order in which `coins` was given, so it only comes out sorted by chance when the coin list happens to be ascending.
