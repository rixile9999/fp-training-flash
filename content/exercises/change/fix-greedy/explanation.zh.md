贪心法假定“现在选最大的硬币，从整体看也是最好的”。对于像韩元这样设计合理的面额，这一点成立；但对 `[1, 4, 15, 20, 50]` 这样的面额就会出错，用 `[4, 5]` 凑 27 时甚至会直接卡住。这种对部分输入正确的代码，靠几个测试很难暴露问题，所以更加危险。

修复方法是不预先决定第一枚硬币。金额 a 的最少枚数是对**所有**硬币 c 求 1 + (a - c 的最少枚数) 后的最小值。这个式子只依赖更小金额的答案，所以从 0 开始依次计算并存进表里，每个金额只算一次，整体在 O(金额 x 硬币种类数) 内完成（`dynamic-programming-subproblems`）。

如果不用表、只用递归写同一个式子，结果是对的，但小金额会被重算无数次，9999 根本算不完。另一个常见错误是用 `result.unwrap(..., 0)` 读取表里没有的金额。“凑不出”变成了“用 0 枚就能凑出”，于是在 `[4, 5]` 下会出现经过 1 或 2 这类不可能金额的荒谬候选。把凑不出的金额留在表外、保持为 `Error(Nil)`，`list.filter_map` 就会自然地把这类候选过滤掉（`errors-as-values`）。
