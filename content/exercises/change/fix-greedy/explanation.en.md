The greedy method assumes that "picking the largest coin right now is also best overall". That holds for well-designed denominations such as Korean won, but it fails for denominations like `[1, 4, 15, 20, 50]`, and with `[4, 5]` and 27 it even gets completely stuck. Code that is right for some inputs is all the more dangerous, because a handful of tests will not expose it.

The fix is not to decide the first coin up front. The fewest coins for amount a is the smallest of 1 + (the fewest coins for a - c) over **every** coin c. This formula depends only on the answers for smaller amounts, so if you compute them in order from 0 and store them in a table, each amount is computed only once and the whole thing finishes in O(amount x number of coin types) (`dynamic-programming-subproblems`).

If you write the same formula as plain recursion without a table, the result is correct, but small amounts get recomputed countless times and 9999 never finishes. Another common mistake is reading amounts missing from the table with `result.unwrap(..., 0)`. "Cannot be made" turns into "can be made with 0 coins", so with `[4, 5]` you get bogus candidates that pass through impossible amounts such as 1 or 2. If you leave unreachable amounts out of the table as `Error(Nil)`, `list.filter_map` filters those candidates out naturally (`errors-as-values`).
