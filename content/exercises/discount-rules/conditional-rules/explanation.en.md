The work is split in two: deciding whether to apply one rule and applying it (`try_rule`), and running several rules in turn while keeping a log (`run_rules`). `try_rule` returns its result as a `Result`, so "applied/skipped" shows up in the type, and `run_rules` only updates the accumulator based on that result. A rule's condition and discount live inside the `Rule` value, so adding a new rule leaves both functions unchanged (theory topic "Higher-order functions and modularity").

The accumulator of `run_rules` is `#(current cart, list of applied names)`. The key point is to check conditions against the **current** cart. If you use the outer argument `cart` as is, the earlier rules' discounts are not reflected: a 52,000 order that dropped to 46,800 after the member discount still gets the "50,000 or more" discount. The habit of using only values taken out of the accumulator inside a fold prevents mistakes like this.

The log is returned as a list instead of being printed. When computation and output are separate, tests only need to compare the list, and the caller decides how to display it (theory topic "Separating computation from effects"). If you collected the names by prepending them, reverse the list at the end with `list.reverse` to restore the order of application.
