When you merge two heaps, the new root is the smaller of the two roots. You keep that heap's left child as is, and attach the result of recursively merging its right child with the other heap as the new child. The recursion only walks down the right branch, so the cost of merge is the sum of the lengths of the two heaps' right branches.

The leftist property keeps this right branch short. If `rank(left) >= rank(right)` at every node, a heap of rank r has at least 2^r - 1 nodes, so the right branch has length O(log n). Keeping this property is done in one place only: `make`. It compares the ranks of the two children, puts the larger one on the left, and sets the node's rank to the smaller rank + 1. `merge`, `insert` (merge with a single node) and `delete_min` (merge the two children) all go through `make`, so the invariant is maintained automatically.

A common mistake is not swapping the children in `make`. The resulting values are correct, but every ascending insert makes the right branch one step longer, so each operation becomes O(n) and the whole run O(n^2). In the performance measurement it is more than a hundred times slower than the reference solution at 8,000 values. If you compute the rank from the left (larger) child, the rank stored in the node no longer matches the definition. Every later placement of children trusts this rank, so the guarantee that the right branch is short loses its basis. If merge forgets the right child and attaches only the other heap, values disappear.

Every operation builds new nodes and shares the existing ones, so the heaps from before a merge can still be used as they were (`persistent-data-structures`). The only new nodes are the O(log n) on the right branch (`cost-model-immutable-structures`).
