A list can only add and remove at the front in O(1). A queue has to add at one end and take out at the other, so with a single list one of the operations becomes O(n). That is why you use two lists. `push` adds to the front of `back`, and `pop` takes from the front of `front`. Both operations touch only the front of a list.

`back` is in reverse insertion order, so when `front` is empty, reversing `back` **once** and moving it into `front` puts the earliest-added item at the front. Reversing is O(k), but each item only goes into `back` once and is moved once when it gets reversed. So the total cost of n operations is O(n), an amortized O(1) per operation. This is a textbook example of amortized analysis (`amortized-analysis`).

There are two common mistakes. If you move `back` into `front` as is without reversing it, the item added later comes out first and the queue behaves like a stack. `to_list` also has to reverse `back` before joining it. And if you write `push` as `list.append(front, [item])`, the result is correct, but every push copies everything, making it O(n^2). In the performance check during grading, it comes out dozens of times slower at 16,000 items.

`push` and `pop` only build a new queue and never touch the previous one. Being able to keep using earlier versions of the queue is the property of a persistent data structure (`persistent-data-structures`). However, if you repeatedly `pop` from the same old version, the reversal can happen every time, so the amortized O(1) guarantee only holds when you use the queue linearly, always continuing from the latest version.
