The original `go` is a direct translation of the definition of edit distance into recursion, so its answers are correct. The problem is that it solves the same subproblems over and over. Every time the characters differ it branches three ways, and different paths arrive at the same (suffix, suffix) pair again. Each extra character multiplies the number of calls, so 250 characters never finishes.

But the two lists `go` receives are always suffixes of the original names, so there are only (250 + 1) x (250 + 1) distinct inputs. A suffix is identified by its remaining length, `#(la, lb)`, so if you store the answer under that key and read it back when the same pair comes up again, each pair is computed only once (`dynamic-programming-subproblems`). Carrying the remaining lengths along as parameters also means you no longer need to recount them with `list.length` every time.

With an immutable `Dict`, "storing" does not happen in place. `dict.insert` returns a new Dict, so `go` returns `#(distance, updated memo)`, and each of the three recursive calls must **take the memo returned by the call before it**, one after another. A common mistake is to pass the original memo to all three calls and throw away the memos they return. Even though the code has a memo, the calls cannot see each other's results, so it is still exponential. Another is to use only the remaining length of `from` as the key: subproblems at different positions in `to` then share one slot and give wrong answers. The key must identify the subproblem **completely**.

You can also fill the same table bottom-up. Building one row at a time from the first row `[0, 1, ..., m]`, as in the base exercise, needs no memo threading and is faster. Top-down memoization has the advantage that you can fix the original recursion while leaving it almost as it is.
