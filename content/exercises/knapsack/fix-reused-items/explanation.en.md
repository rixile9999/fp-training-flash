In the 0/1 knapsack table, cell w of the new table is the larger of "don't load this parcel (cell w of the previous table)" and "load this parcel (cell (w - weight) of the previous table + value)". Both values must be read from the table **before this parcel was considered** (`dynamic-programming-subproblems`).

The original code read from `table`, the one passed in by `int.range`, which is the table currently being built. It fills the cells going up through the limits 3, 4, 5, ..., so by the time it computes the cell for limit 6, the cell for limit 3 it reads already contains this parcel. That is how a single parcel went into cell 3 → cell 6 → cell 9 again and again, giving a value of 30. This is the calculation for the "unbounded knapsack", where each parcel can be used any number of times.

The fix is to read from `previous` instead. With an immutable `Dict`, `previous` stays as it is even after you `dict.insert` into the new table, so you can use both tables at the same time (`immutability-structural-sharing`). To get the same effect while overwriting a single array in an imperative language, you would have to go through the limits **backwards, from the largest**; with an immutable data structure you can write "read from the previous table" directly as code, without that trick.

There are two common half-fixes. If you switch only the "don't load" side to `previous`, the "load" side still reads the new table and keeps loading the same parcel. If, on the other hand, you also write into `previous`, each cell throws away the updates of the earlier cells and the result comes up short. Read from the previous table, write to the new one.
