구조는 주문 한 줄 파싱과 같습니다. 필드를 나누고 개수를 `case` 패턴으로 확인한 뒤, 필드마다 `Result`를 돌려주는 함수를 `use`와 `result.try`로 연결합니다. 앞 단계가 실패하면 뒤 단계는 실행되지 않으므로 검사 순서가 코드 순서와 같아집니다(**Result 연결과 모나드(chaining-results-monads)** 주제).

이 문제에서 새로운 부분은 두 가지입니다.

- **문자열을 커스텀 타입으로 바꾸기.** `parse_reason`은 알려진 문자열을 생성자로 옮기고, 나머지를 `UnknownReason`으로 보냅니다. 이렇게 경계에서 한 번 바꿔 두면 이후 코드는 `Reason`의 세 경우만 다루면 되고, 컴파일러가 빠진 경우를 알려 줍니다(**합 타입과 빠짐없는 분기** 주제). 비교는 `string.lowercase`한 값으로 하되, 오류에는 원래 필드를 담아 사용자가 입력한 그대로 보여 줍니다.
- **양쪽 경계가 있는 범위.** `Ok(amount) if amount >= 1 && amount <= max_amount`처럼 가드 하나에 두 조건을 모두 적습니다. 상한은 "이하"이므로 1,000,000은 허용됩니다.

자주 하는 실수:

- 사유를 대소문자 그대로 비교해 `"Wrong_Item"`을 거부한다.
- 상한을 `<`로 적어 정확히 1,000,000인 요청을 거부한다(경계값 하나 차이).
- 하한만 검사하고 상한을 잊는다.
