`resolve`는 세 단계의 조회를 서로 다른 방식으로 연결합니다.

- **프로필 찾기는 `result.try`로 연결합니다.** 실패하면 거기서 끝나야 하기 때문입니다. 없는 프로필 이름은 대부분 오타이므로, default로 대체하면 실수가 숨겨집니다.
- **키 찾기는 `result.lazy_or`로 연결합니다.** 프로필에 키가 없는 것은 정상적인 상황이고, 그때만 default를 봅니다. `lazy_or`는 앞 결과가 `Error`일 때만 함수를 실행하므로 우선순위(프로필 → default)가 코드 순서 그대로 드러납니다.
- 마지막에 `result.replace_error(MissingKey(key))`로 "어디에도 없음"을 이 문제의 오류로 바꿉니다. `from_default`가 `Result(String, Nil)`을 돌려주므로 default 프로필이 없는 경우도 같은 길로 처리됩니다.

`try`는 "성공하면 계속", `lazy_or`는 "실패하면 대안"입니다. 두 연결을 구분해 쓰는 것이 **Result 연결과 모나드(chaining-results-monads)** 주제의 실전 모습입니다.

`resolve_int`는 대체 규칙을 다시 구현하지 않고 `resolve`의 결과에 `int.parse`만 이어 붙입니다. 그래서 "값을 찾는 규칙"과 "값을 해석하는 규칙"이 섞이지 않습니다. 찾은 값이 잘못됐다면 그것은 설정 실수이므로 `NotAnInt`로 알려야 합니다(**오류도 값이다** 주제).

자주 하는 실수:

- 없는 프로필을 빈 설정처럼 다뤄 default 값을 돌려준다.
- `resolve_int`에서 "프로필 값을 정수로 바꾸고, 실패하면 default"처럼 파싱 실패까지 대체 대상으로 삼는다. 잘못 적힌 운영 설정이 조용히 기본값으로 바뀝니다.
- default를 먼저 찾아 프로필 값이 무시된다.
