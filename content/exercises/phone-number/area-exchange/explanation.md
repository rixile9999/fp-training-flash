검사 함수 두 개가 모두 `fn(String) -> Result(String, PhoneError)` 모양입니다. 통과하면 받은 번호를 그대로 돌려주고, 실패하면 이유를 담은 오류를 돌려줍니다. 모양이 같으므로 `result.try`로 줄줄이 이을 수 있습니다.

```gleam
pub fn clean(input: String) -> Result(String, PhoneError) {
  normalize(input)
  |> result.try(check_area_code)
  |> result.try(check_exchange_code)
}
```

파이프의 순서가 곧 명세의 순서입니다. 앞 단계가 `Error`를 내면 뒤 단계는 실행되지 않고 그 오류가 그대로 나옵니다. 검사를 하나 더 추가할 때도 줄 하나만 붙이면 됩니다.

각 검사 함수는 "정리된 10자리 번호"를 받는다고 가정합니다. 이 가정 덕분에 함수 안에서는 구분 기호나 국가 번호를 신경 쓰지 않고 `string.slice(number, 0, 1)`, `string.slice(number, 3, 1)`로 원하는 숫자만 보면 됩니다. 그 가정을 지키는 책임은 `clean`에 있습니다. `normalize`를 반드시 먼저 거쳐야 합니다.

흔한 실수는 네 가지입니다.

- 예시에 나온 숫자만 막는 것. 규칙은 "첫 숫자가 `2`–`9`"이므로 두 코드 모두 `0`과 `1`을 함께 막아야 합니다. 허용 범위를 기준으로 생각하면 빠뜨리지 않습니다.
- 교환 번호 위치를 잘못 잡는 것. 교환 번호는 네 번째 숫자이고, 0부터 세면 위치 3입니다.
- 원래 입력에 먼저 검사를 적용하고 정리를 나중에 하는 것. `"1 (223) 456-7890"`의 첫 글자 `1`은 국가 번호인데 지역 번호로 오인됩니다. `"023"`처럼 짧은 입력도 길이 오류 대신 지역 번호 오류가 나옵니다.
- 두 검사의 순서를 바꾸는 것. 둘 다 틀린 번호에서 다른 오류가 보고됩니다.

같은 모양의 실패 가능한 단계를 이어 붙이는 방식은 이론 노트 "Result 연결과 모나드"(chaining-results-monads)에서 더 다룹니다.
