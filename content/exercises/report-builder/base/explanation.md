리포트 작업은 데이터의 모양이 세 번 바뀝니다. `String` 한 줄은 `Result(Sale, Nil)`이 되고, `Sale` 목록은 `#(카테고리, 합계)` 목록이 되고, 마지막에 다시 `String`이 됩니다. 모양이 바뀌는 지점마다 함수 하나를 두면 각 함수의 입력과 출력 타입만 보고도 무엇을 하는지 알 수 있고, 테스트도 단계별로 따로 할 수 있습니다. 세 함수 모두 같은 입력에 같은 결과를 돌려주는 순수 함수이므로 `build_report`의 결과는 세 함수를 차례로 적용한 값과 정확히 같습니다(이론 주제 "참조 투명성").

`build_report`는 파이프로 `parse_line → total_by_category → format_row`를 잇기만 합니다. 이 순서가 곧 처리 순서이므로 코드를 위에서 아래로 읽으면 흐름이 보입니다(이론 주제 "함수 합성과 파이프라인"). 잘못된 줄을 건너뛰는 일은 `list.filter_map(parse_line)`이 맡습니다. `parse_line`이 실패를 `Error`로 돌려주기 때문에 건너뛸지 말지는 호출하는 쪽이 정할 수 있습니다.

흔한 실수는 두 가지입니다.

- 금액을 읽지 못했을 때 `0`으로 바꿔 `Ok`를 돌려주는 것. 그러면 잘못된 줄의 카테고리가 `toys: 0`처럼 리포트에 나타납니다. 실패는 실패로 돌려주고 결정은 호출자에게 맡기세요.
- 집계 결과를 처음 등장한 순서로 두는 것. 순서도 요구 사항이므로 `list.sort`와 `string.compare`로 명시적으로 정렬합니다. `dict.to_list`의 순서는 보장되지 않습니다. 키가 적을 때는 우연히 이름순으로 나오기도 해서 작은 예제로는 드러나지 않지만, 카테고리가 많아지면 순서가 뒤섞입니다. 그러니 정렬을 생략하면 안 됩니다.
