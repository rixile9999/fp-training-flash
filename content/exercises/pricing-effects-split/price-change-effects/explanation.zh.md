现有的 `update_price` 在一个函数里完成了价格计算、降价率判断、打印记录和发送通知。打印和通知都是效应，测试无从得知“谁收到了什么”。这次的解决办法是把效应变成 **只描述、不执行的值**。

```gleam
pub type Effect {
  Log(message: String)
  Notify(customer: String, message: String)
}
```

`change_price` 返回新商品以及一份“要做的事”列表。这个列表就是普通的数据，可以用 `should.equal` 连顺序一起比较，而且无论调用多少次都不会发生任何事。真正的执行只在 `update_price` 一处，通过 `list.each(effects, run)` 完成。以后即使把通知改成电子邮件，也只需修改 `run`，计算逻辑和测试都保持不变。

把降价率的计算拆成 `drop_percent`，就能单独检查规则的边界。价格上涨时公式会得出负数，所以必须限制为 0。原价小于等于 0 时，按规则也返回 0。Gleam 的整数除法在除以 0 时返回 0 而不是报错，但与其依赖这个性质，不如把条件明确写出来，读代码的人更能看清意图。标准是“20% 及以上”，所以写 `>= 20`。

常见错误是用 `fold` 像 `[Notify(..), ..acc]` 这样把通知加到前面来构建列表。这样通知的顺序会颠倒，记录也会被挤到最后。为每个元素生成一个值，应该用保持顺序的 `list.map`；记录则用 `[log, ..notices]` 放在最前面。

用数据表示效应、把执行推迟到边缘，这种设计正是理论笔记“分离计算与效应”的核心。
