연산 하나의 최악 비용만 보면 지나치게 비관적인 경우가 있다. 대부분은 싸고 가끔만 비싼 연산이라면, 연산을 **여러 번 이어서** 했을 때의 총비용이 더 정확한 척도다. 어떤 연산 순서에 대해서든 m번의 총비용이 m × c 이하라면, 그 연산의 **상각 비용**은 c다.

상각 비용은 평균 사례 분석과 다르다. 입력 분포나 확률을 가정하지 않고, 가능한 **모든** 연산 순서에 대해 성립하는 보장이다.

## 예: 이진 카운터

낮은 자리부터 저장한 이진수에 1을 더한다. 가장 낮은 자리부터 이어지는 1을 0으로 바꾸다가 처음 만나는 0을 1로 바꾼다.

```gleam
/// [1, 1, 0, 1]은 1 + 2 + 8 = 11이고, 결과 [0, 0, 1, 1]은 12다.
pub fn increment(bits: List(Int)) -> List(Int) {
  case bits {
    [] -> [1]
    [0, ..rest] -> [1, ..rest]
    [_, ..rest] -> [0, ..increment(rest)]
  }
}
```

한 번의 비용은 가장 낮은 자리부터 연속된 1의 개수 + 1이다. 모든 자리가 1이면 자릿수만큼, 즉 O(log n)이 든다. 하지만 0부터 n번 더하는 동안 맨 끝 자리는 매번, 그다음 자리는 두 번에 한 번, 그다음은 네 번에 한 번 바뀐다. 총 변경 횟수는 n + n/2 + n/4 + ... < 2n이므로 상각 비용은 O(1)이다.

## 은행가 방법: 싼 연산이 저금한다

각 연산에 실제 비용보다 조금 큰 **상각 비용**을 매기고, 남는 몫을 자료구조 안에 **크레딧**으로 저금한다. 비싼 연산은 저금해 둔 크레딧으로 비용을 치른다. 크레딧이 한 번도 음수가 되지 않으면 실제 총비용은 상각 비용의 합을 넘지 않는다.

이진 카운터에서는 0을 1로 바꿀 때 비용 1을 내고 그 자리에 크레딧 1을 올려 둔다. 나중에 그 1을 0으로 바꾸는 비용은 올려 둔 크레딧이 낸다. 한 번 더할 때 0을 1로 바꾸는 일은 많아야 한 번이므로 상각 비용은 2다.

## 예: 목록 두 개로 만든 큐

큐는 앞에서 빼고 뒤에 넣는다. 목록 하나로는 뒤에 넣는 비용이 O(n)이다. 그래서 빼는 쪽 목록 `front`와 넣는 쪽 목록 `back`을 따로 둔다. `back`에는 새 원소를 앞에 붙이므로(O(1)) 넣은 순서의 역순으로 쌓인다. 뺄 때 `front`가 비어 있으면 `back`을 뒤집어 `front`로 옮긴다.

| 연산 | `front` | `back` | 실제 비용 |
|---|---|---|---|
| 1 넣기 | `[]` | `[1]` | 1 |
| 2 넣기 | `[]` | `[2, 1]` | 1 |
| 3 넣기 | `[]` | `[3, 2, 1]` | 1 |
| 빼기 → 1 | `[2, 3]` | `[]` | 3(뒤집기) + 1 |
| 4 넣기 | `[2, 3]` | `[4]` | 1 |
| 빼기 → 2 | `[3]` | `[4]` | 1 |

뒤집기는 가끔 O(k)가 들지만, 원소 하나는 `back`에서 `front`로 **딱 한 번**만 옮겨진다. 넣을 때 크레딧 1을 원소에 붙여 두면 그 원소의 뒤집기 비용은 이미 치러진 셈이다. 따라서 넣기와 빼기를 어떤 순서로 m번 해도 총비용은 O(m)이고, 두 연산 모두 상각 O(1)이다.

## 영속적으로 쓰면 보장이 깨진다

은행가 방법은 저금한 크레딧을 **한 번만** 쓴다고 가정한다. 불변 자료구조에서는 옛 버전이 그대로 남아 있으므로 이 가정이 깨질 수 있다. `front`가 비고 `back`에 원소가 1000개 있는 큐 `q`가 있을 때, 같은 `q`에서 빼기를 100번 호출하면 호출마다 1000개를 다시 뒤집는다. 저금은 한 번 했는데 인출은 100번 한 셈이다. 이진 카운터도 모든 자리가 1인 같은 값에 `increment`를 반복하면 매번 자릿수만큼 든다.

반복문에서 항상 가장 최근 버전만 이어서 쓴다면(대부분의 큐 사용이 그렇다) 상각 보장은 그대로 성립한다. 옛 버전을 되풀이해 쓰는 경우에도 보장이 필요하다면 지연 평가와 메모이제이션을 이용하는 방법이 있으며, Okasaki가 이를 자세히 다룬다.

## 이 개념이 쓰이는 곳

- 너비 우선 탐색의 큐처럼 넣기와 빼기가 섞여 계속 반복되는 곳.
- 가끔 뒤집거나 재구성하는 자료구조의 비용을 설명할 때.
- 반대로 목록 뒤에 `list.append`로 하나씩 붙이는 것은 상각해도 O(n)이다. 비싼 작업이 가끔이 아니라 매번 일어나기 때문이다.
