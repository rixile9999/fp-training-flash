id: immutability-structural-sharing
title: 不可变值与结构共享
---
Gleam 的值一旦创建就不会改变。往列表里加一项、修改记录的字段，这些操作都不会修改原值，而是返回一个**新值**。持有原值的一方看到的始终是同一个值。

每次都构造新值听起来很慢，但没有变化的部分不会被复制，而是被**共享**，所以大多数时候代价很小。用 `[x, ..xs]` 在列表前面加一项，只新建一个格子，并原样指向整个 `xs`。

```gleam
pub fn shared_tails() -> #(List(Int), List(Int), List(Int)) {
  let base = [2, 3]
  let a = [1, ..base]
  let b = [9, ..base]
  #(base, a, b)
}
```

`a` 和 `b` 共享同一个 `base` 作为尾部。谁都改不了 `base`，所以共享是安全的。如果是可变列表，一方的修改就会泄漏到另一方，只能防御性地复制。

记录更新也是一样。`Order(..order, amount: 0)` 只构造一个包含几个字段的新记录，没有变化的字段的值（比如很长的 `items` 列表）不会被复制，而是指向同一个值。

```gleam
pub type Order {
  Order(id: Int, items: List(String), amount: Int)
}

pub fn clear_amount(order: Order) -> Order {
  Order(..order, amount: 0)
}
```

## 需要付出代价的情况

只有当“没有变化的部分”位于新值的**末尾一侧**时，共享才成立。用 `list.append(xs, [x])` 加到列表末尾，必须新建 `xs` 的所有格子，所以是 O(n)。如果像循环那样一个一个地加到末尾，总代价就变成 O(n²)。所以函数式代码的做法是加在前面收集，最后调用一次 `list.reverse`。

## 不可变性带来的好处

- **推理是局部的**：把值传给函数，那个函数也改不了你的值。在测试里，不必担心调用之后原输入是否还完好。
- **旧版本会保留**：可以同时持有更新前和更新后的值，比较、撤销、保存历史都很容易。
- **共享是安全的**：即使多处持有同一个值，谁也改不了它，所以不需要防御性复制或加锁。

常见的错误是误以为“更新了却没生效”。调用 `clear_amount(order)` 后把返回值扔掉，就什么也不会发生。新值必须绑定到变量上，或者传给下一步。

## 这个概念用在哪里

- 用记录更新语法构造只改了部分字段的新值时。
- 构造列表时，选择加在前面、最后反转的模式时。
- 设计持久化数据结构时，核心思想就是只新建被更新的部分，其余部分共享。
