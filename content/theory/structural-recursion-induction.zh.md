title: 结构递归与归纳法
---
递归函数的形状来自数据类型的定义。Gleam 的列表要么是空列表 `[]`，要么是一项加上剩余列表 `[x, ..rest]`。所以处理列表的函数为这两种情况各设一个分支，并且只对**更小的部分** `rest` 进行递归调用。这就是结构递归。

```gleam
pub fn total(xs: List(Int)) -> Int {
  case xs {
    [] -> 0
    [x, ..rest] -> x + total(rest)
  }
}
```

这种形状提供两个保证。

- **终止**：每次调用列表都短一格，而列表是有限的，所以最终一定会到达 `[]` 分支。
- **正确性**：可以用与数学归纳法相同的结构来推理。先确认 `[]` 时答案是否正确（基础步骤）。然后**假设** `total(rest)` 能正确返回 `rest` 的和，再确认这时 `x + total(rest)` 是否是整个列表的和（归纳步骤）。两个步骤都成立，对所有列表就都成立。

这就是写递归函数时不必在脑子里把调用过程一路展开的原因。只需回答：“如果剩余部分的答案已经有了，当前这一格该怎么处理？”

如果类型有多个分支，递归调用也会有多次。树的左子树和右子树都是更小的结构，所以两边都要递归调用。

```gleam
pub type Tree {
  Leaf
  Node(left: Tree, value: Int, right: Tree)
}

pub fn size(tree: Tree) -> Int {
  case tree {
    Leaf -> 0
    Node(left, _, right) -> size(left) + 1 + size(right)
  }
}
```

常见的错误有三种。第一，基础步骤的值定错了（比如把空列表的和定为 1）。完全漏掉 `[]` 分支时编译器会发现，但值错了它发现不了。第二，用没有变小的值递归。用同一个列表再次调用，或者整数跳过了基础值继续变小，都会永不结束。第三，把 `[x]` 这样的特殊情况不必要地单独处理，导致各分支之间的规则不一致。用整数 `n` 递归时，`n - 1` 也必须是“更小的自然数”，所以要先挡住负数输入。

上面的 `total` 在递归调用之后还要做加法，所以不是尾递归。在 BEAM 上，栈不会因为大小固定而溢出，而是按需增长，但会占用与输入长度成正比的内存。对于很长的输入，可以改成使用累加器的尾递归（参见“累加器与尾递归”）。

## 这个概念用在哪里

- 设计处理列表、树和自定义递归类型的函数时，为每个构造器各设一个分支。
- 检查递归函数是否正确时，把基础步骤和归纳步骤分开推理。
- 把结构递归的共同形状抽象出来，就是 fold（参见“fold 的普适性”）。
