title: 摊还分析：偶尔昂贵的操作的真实代价
---
只看单次操作的最坏代价，有时会过于悲观。如果一个操作大多数时候很便宜、只是偶尔昂贵，那么**连续执行多次**的总代价才是更准确的衡量标准。如果对任何操作序列，m 次操作的总代价都不超过 m × c，那么这个操作的**摊还代价**就是 c。

摊还代价不同于平均情况分析。它不假设任何输入分布或概率，而是对**所有**可能的操作序列都成立的保证。

## 例子：二进制计数器

给一个从低位开始存储的二进制数加 1。从最低位开始，把连续的 1 都变成 0，再把遇到的第一个 0 变成 1。

```gleam
/// [1, 1, 0, 1] 是 1 + 2 + 8 = 11，结果 [0, 0, 1, 1] 是 12。
pub fn increment(bits: List(Int)) -> List(Int) {
  case bits {
    [] -> [1]
    [0, ..rest] -> [1, ..rest]
    [_, ..rest] -> [0, ..increment(rest)]
  }
}
```

一次调用的代价是从最低位开始连续 1 的个数再加 1。如果所有位都是 1，代价就等于位数，即 O(log n)。但从 0 开始加 n 次的过程中，最低位每次都变，下一位每两次变一次，再下一位每四次变一次。总变化次数是 n + n/2 + n/4 + ... < 2n，所以摊还代价是 O(1)。

## 银行家方法：便宜的操作先存钱

给每个操作定一个比实际代价稍大的**摊还代价**，把多出来的部分作为**信用**（credit）存进数据结构里。昂贵的操作用存下的信用来支付。只要信用从不为负，实际总代价就不会超过摊还代价之和。

在二进制计数器中，把 0 变成 1 时支付代价 1，同时在这一位上存下 1 份信用。以后把这个 1 变回 0 的代价，就由存下的信用支付。每次加 1 最多只把一个 0 变成 1，所以摊还代价是 2。

## 例子：用两个列表实现的队列

队列从前面取出、从后面放入。只用一个列表的话，放到后面的代价是 O(n)。所以分别维护负责取出的列表 `front` 和负责放入的列表 `back`。新元素加在 `back` 的前面（O(1)），因此 `back` 按放入顺序的逆序堆积。取出时如果 `front` 为空，就把 `back` 反转后移到 `front`。

| 操作 | `front` | `back` | 实际代价 |
|---|---|---|---|
| 放入 1 | `[]` | `[1]` | 1 |
| 放入 2 | `[]` | `[2, 1]` | 1 |
| 放入 3 | `[]` | `[3, 2, 1]` | 1 |
| 取出 → 1 | `[2, 3]` | `[]` | 3（反转）+ 1 |
| 放入 4 | `[2, 3]` | `[4]` | 1 |
| 取出 → 2 | `[3]` | `[4]` | 1 |

反转偶尔要花 O(k)，但每个元素从 `back` 移到 `front` **恰好只有一次**。如果放入时给元素附上 1 份信用，这个元素的反转代价就已经提前付过了。因此，无论以什么顺序执行 m 次放入和取出，总代价都是 O(m)，两种操作的摊还代价都是 O(1)。

## 持久化地使用会破坏保证

银行家方法假设存下的信用**只用一次**。在不可变数据结构中，旧版本会原样保留，这个假设就可能被打破。设有一个队列 `q`，它的 `front` 为空，`back` 里有 1000 个元素。对同一个 `q` 调用 100 次取出，每次调用都要重新反转这 1000 个元素。相当于只存了一次钱，却取了 100 次。二进制计数器也一样：对同一个所有位都是 1 的值反复调用 `increment`，每次的代价都等于位数。

如果循环里总是接着使用最新版本（大多数队列的用法都是这样），摊还保证依然成立。如果反复使用旧版本时也需要保证，可以借助惰性求值和记忆化，Okasaki 对此有详细论述。

## 这个概念用在哪里

- 像广度优先搜索中的队列那样，放入和取出交替进行、不断重复的地方。
- 解释偶尔需要反转或重建的数据结构的代价。
- 反过来，用 `list.append` 往列表末尾逐个追加，即使摊还也是 O(n)，因为昂贵的工作不是偶尔发生，而是每次都发生。
